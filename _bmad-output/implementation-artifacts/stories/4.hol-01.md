## Dev Notes

### Architecture
- Follow existing patterns from `BellScheduleService` and `TermService`
- `holiday_calendars` stores one calendar per academic year per tenant — enforced via UNIQUE(tenant_id, academic_year_id) + service-level check
- `holiday_dates` CRUD is out of scope for HOL-01 (future stories); only create entity + migration
- Validate academicYearId exists in tenant using `academicYearRepository.findByIdAndTenantId()` — throw ResourceNotFoundException (404) if not found
- Write operations: `@PreAuthorize("hasAnyRole('ADMIN', 'MOD')")` on POST/PUT/DELETE
- Read operations: no @PreAuthorize (security config enforces authentication already)

### Key Technical Details
- Entity IDs: `Long` with `GenerationType.IDENTITY`
- `holiday_dates.date` column: use `java.time.LocalDate`
- `holiday_dates.type` column: `VARCHAR(30)` in DB, mapped via `@Enumerated(EnumType.STRING)` in entity
- Conflict on duplicate calendar: throw `ConflictException` ("Holiday calendar already exists for this academic year")
- Cascade: deleting a HolidayCalendar cascades to holiday_dates via ON DELETE CASCADE in migration
- `holiday_calendars.academic_year_id` → `academic_years(id)` uses `ON DELETE CASCADE`, matching `terms` (V006): deleting an academic year removes its holiday calendar (and nested `holiday_dates` via the calendar FK)

### Test Infrastructure
- Endpoint tests: register admin, create MOD user (via invite + role update), create TEACHER user, create other-tenant admin
- Need to create an academic year before testing holiday calendars
- Service tests: mock AcademicYearRepository + HolidayCalendarRepository
