# Story TMPL-01 — Template Data Model
**Epic:** Epic 10 — Setup Templates (Post-MVP) | **Points:** 3 SP | **Status:** done

## Description
Template data model + Flyway migration; `institution_templates` table with embedded configuration JSONB

## Acceptance Criteria
- [x] `V033__create_institution_templates.sql` Flyway migration creates `institution_templates` table
- [x] Schema: id, name, description, institutionType, configurationJson (JSONB), isBuiltIn, tenantId (nullable for built-ins)
- [x] JSONB configuration stores: bellSchedule, settings, terminology, constraintDefaults
- [x] Built-in templates have `tenant_id = NULL` and `is_built_in = true`
- [x] Custom templates scoped to tenant with `is_built_in = false`
- [x] API: `GET /api/v1/templates` lists available templates (built-in + tenant's own)

## Technical Notes
Built-ins seeded via TMPL-02. JSONB schema validated on write.

## Dev Agent Record

### Implementation Plan
- `configuration_json` is JSONB, matching `tenants.settings` from V001; H2 runs in PostgreSQL compatibility mode for tests and the column is read and written as text either way.
- A DB CHECK enforces the ownership rule the ACs describe: a built-in has no tenant, a custom template must have one. Neither state can be created by accident.
- **`InstitutionTemplate` is deliberately not tenant-filtered.** Built-ins carry `tenant_id = NULL`, so the usual Hibernate `tenantFilter` would hide exactly the rows everyone is meant to see. Visibility is decided in the repository query instead — built-ins, plus the caller's own when a tenant is known.
