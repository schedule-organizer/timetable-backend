**Epic:** Epic 6 — Timetable & Scheduling Engine | **Points:** 5 SP | **Status:** done

## Description
`ConflictDetectionService` — real-time constraint checks: teacher double-booking, room double-booking, class double-booking, room capacity, forbidden slots

## Acceptance Criteria
- [x] `checkConflicts(lesson, proposedPeriodId, proposedRoomId)` returns list of `ConflictViolation` objects
- [x] Checks: teacher already assigned in period, room already booked in period, class already scheduled in period, room capacity < group size, teacher/room/class forbidden slot
- [x] Returns empty list if no conflicts
- [x] Used by SCHED-08 (move), SCHED-10 (swap), HOL-07 (holiday conflict)
- [x] Performance: completes in < 50ms for typical school size (< 500 lessons)

## Dev Agent Record

### Implementation Plan
- Extends the existing HOL-07 service rather than adding a second one, as its own javadoc anticipated. The holiday query is untouched.
- `checkConflicts(lesson, proposedPeriodId, proposedRoomId)` takes both proposals as nullable, where null means "keep what the lesson has". One method therefore answers both "is this lesson OK where it is?" (the grid's `hasConflict`) and "would this move be OK?" (SCHED-08/10) — they can never diverge.
- Two queries per call regardless of school size: the occupants of the target slot, and the forbidden slots on that period. Everything else is in-memory comparison, which is what makes the < 50ms AC achievable.
- Conflicts are scoped to the lesson's own timetable, per the story's technical note. A DRAFT being edited therefore does not collide with the PUBLISHED timetable for the same term.
- A single occupant can raise several violations at once (same teacher *and* same class *and* same room), and all are returned rather than short-circuiting — the caller gets the full picture.

### Completion Notes
- **`lessons` gained three columns here** (V027) rather than in SCHED-02 where V015's comment anticipated them. Conflict detection is the first consumer: room double-booking and room-capacity checks are impossible without `room_id`. `is_pinned` (SCHED-09) and `version` (SCHED-08 optimistic locking) ride along in the same migration to avoid three separate ALTERs.
- `room_id` is nullable and unset capacities are never violations — the solver may leave a lesson unroomed, and an unknown capacity is not evidence of a problem.
- Forbidden slots identify a teacher by `teachers.id` while a lesson carries `users.id`, so the service maps user → teacher profile. A user with no teacher profile simply skips teacher-forbidden checks instead of failing.
- An unparseable `entity_type` is skipped rather than thrown, matching the defensive reads elsewhere in the codebase.
- `./mvnw -o test -Dtest='ConflictDetectionServiceSchedTest,ConflictDetectionServiceTest'` → 20 passed.
