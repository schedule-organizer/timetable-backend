# Story SCHED-03 — Async Solver Engine
**Epic:** Epic 6 — Timetable & Scheduling Engine | **Points:** 8 SP | **Status:** done

## Description
`POST /api/v1/engine/run` — async solver job: load problem from DB → build `TimetableSolution` → call `SolverManager.solveAndListen` → return `jobId` immediately; sensitivity and mode parameters

## Acceptance Criteria
- [x] Accepts: timetableId, mode (FAST/BALANCED/THOROUGH), timeout override (optional)
- [x] Loads all resources (teachers, rooms, classes, subjects, forbidden slots, holidays) from DB
- [x] Builds Timefold `TimetableSolution` domain model
- [x] Starts async solver via `SolverManager.solveAndListen`
- [x] Returns `jobId` immediately (non-blocking)
- [x] Only one active solver job per timetable at a time (409 if already running)
- [x] Timeout enforced per subscription tier (Starter: 30s, Professional: 2min, Enterprise: 10min)

## Technical Notes
In-process JVM solver (TD-01). `AsyncConfig` isolates solver thread pool. Solver constraints defined as Timefold `ConstraintProvider`.

## Dev Agent Record

### Implementation Plan
- `SolverProblemBuilder` assembles the Timefold problem from persisted rows; `SolverService` owns the run/track lifecycle; `SolverResultWriter` persists callbacks. Split three ways because Timefold invokes callbacks on its own threads, which carry no transaction and no `TenantContext`, so those writers must take every id explicitly and open their own transactions.
- Timeout is applied per job via `SolverConfigOverride` + `TerminationConfig`, so one shared `SolverManager` serves runs of different lengths.
- One active job per timetable is enforced by querying QUEUED/RUNNING rows before inserting (409).

### Debug Log
- Two tests failed because `REQUIRES_NEW` callbacks could not see the job row while `run()`'s own transaction was still open: the empty-timetable path reported QUEUED, and a finished job could still be cancelled. Fixed structurally — the empty and RUNNING status writes now happen in the request transaction, and the solver is only started from an `afterCommit` synchronisation. That also closes a real race where a very fast solve could have completed before its own job row was visible.

### Completion Notes
- **Subscription tiers do not exist in this codebase** — no column, enum or config anywhere. The AC's three timeouts (30s / 2min / 10min) are carried by `SolverMode` FAST / BALANCED / THOROUGH instead, with an optional per-request override capped at one hour. Binding them to a real tier is a product decision; recorded in `deferred-work.md`.
- **The solver rearranges existing lessons; it does not generate them.** The placeable dates are the ones the timetable's lessons already occupy. Creating lessons from `class_subject_hours` is a distinct problem no Epic 6 story specifies — also recorded as deferred.
- Problem facts wired: holiday penalties (HOL-05), teacher–subject qualifications (RES-05), option-block memberships (RES-08). `@PlanningPin` now honours SCHED-09's pins, closing that story's deferred item.
- Empty timetables complete immediately rather than starting a solver with nothing to move.
