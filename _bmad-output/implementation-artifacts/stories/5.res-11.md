# Story RES-11 — CSV Bulk Import
**Epic:** Epic 5 — Resource Management | **Points:** 8 SP | **Status:** done

## Description
CSV bulk import endpoint — parse and upsert Rooms, Classes, Teachers via multipart upload; return row-level error report

## Acceptance Criteria
- [x] `POST /api/v1/import/{entityType}` accepts multipart CSV file (entityType: rooms, classes, teachers)
- [x] Parses CSV, validates each row, upserts valid rows (insert or update by name)
- [x] Returns row-level error report: `{ row, field, error }` for each failure
- [x] Partial success: valid rows imported even if some rows fail
- [x] Max file size: 5MB; max rows: 1000
- [x] Returns 400 for malformed CSV or unrecognised entityType
- [x] Admin/Mod only

## Technical Notes
Use Apache Commons CSV or OpenCSV. Process in a single transaction per valid row (not all-or-nothing). Return summary: imported, updated, skipped, errors.

- [x] `commons-csv` 1.11.0 dependency; `spring.servlet.multipart` limits raised to 5MB / 6MB

## Dev Agent Record

### Implementation Plan
- Columns (case-insensitive headers):
  - **rooms** — `name`*, `type`*, `capacity`, `building`, `floor`, `equipmentTags` (pipe-separated, matching `StringListConverter`)
  - **classes** — `name`*, `yearLevel`, `capacity`, `homeroom` (an existing room name, resolved to `homeroom_id`)
  - **teachers** — `email`*, `displayName`*, `maxPeriodsPerDay`, `maxConsecutivePeriods`, `workloadCap`
- Two failure levels. File-level problems reject the upload with 400: unknown entity type, empty file, over 5MB, more than 1000 rows, unparseable CSV, missing required column, duplicate column. Row-level problems become `{row, field, error}` entries and skip only that row.
- `CsvRowWriter` is a separate `@Component` so its `@Transactional(REQUIRES_NEW)` methods go through the proxy — self-invocation from `CsvImportService` would have silently lost the per-row transaction boundary the story asks for.
- `row` in the error report is the 1-based line in the uploaded file (header is line 1), which is what the user sees in a spreadsheet, not the parser's record index.
- `DuplicateHeaderMode.DISALLOW` is set explicitly; Commons CSV 1.10+ allows duplicates by default, which would let a repeated column silently shadow the earlier one.

### Debug Log
- `duplicateHeaders_throwBadRequest` initially failed: Commons CSV 1.11 permits duplicate headers by default. Fixed by setting `DuplicateHeaderMode.DISALLOW` on the format.

### Completion Notes
- Upsert keys: rooms and classes by `name` within the tenant, as the AC specifies. **Teachers are keyed by `email`**, not by name — a teacher profile is uniquely tied to a user (`teachers.user_id` is one-per-tenant), the CSV must name that user anyway to create a profile, and `display_name` is not unique. An unknown email or one belonging to another tenant is a row-level error. Re-importing a deactivated teacher reactivates the profile.
- `spring.servlet.multipart.max-file-size` defaults to 1MB, which would have rejected valid uploads well under the story's 5MB limit before the service ever saw them; raised to 5MB with the request cap at 6MB. The service still checks the size itself so the error message is the story's, and the new `MaxUploadSizeExceededException` handler turns a container-level rejection into a 400 rather than a 500.
- `./mvnw -o test -Dtest='CsvImportServiceTest'` → 13 passed; `-Dtest='CsvRowWriterTest'` → 15 passed; `-Dtest='CsvImportEndpointTest'` → 14 passed.
- **Fixed an unrelated pre-existing failure.** The first full-suite run of the epic surfaced `ClassSubjectHourServiceTest.replace_duplicateSubject_throws` failing with `ResourceNotFoundException` instead of `BadRequestException`. Reproduced at commit `8bd3c1c` (RES-06) in a scratch worktree, so it predates this story — RES-06's completion notes record that the full suite was never run in that environment. The production path is correct; the test just never stubbed the subject lookup, so validation threw on the first item before the duplicate check on the second could run. Added the missing stub.
