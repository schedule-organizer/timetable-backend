# Story SCHED-13 — Schedule Checkpoints (Save & Restore)
**Epic:** Epic 6 — Timetable & Scheduling Engine | **Points:** 5 SP | **Status:** done

## Description
Implement **FR26–FR27**: MODERATOR (and ADMIN) can save a **named checkpoint** of the current timetable state and **restore** the timetable to any prior checkpoint. Supports the PRD innovation around checkpoint/rollback as a scheduling primitive.

**Traceability:** FR26, FR27, FR29 (version status — align with existing `DRAFT`/`PUBLISHED` model); Domain §Checkpoint safety.

## Acceptance Criteria
- [x] New persistence: e.g. `timetable_checkpoints` table — `id`, `tenant_id`, `timetable_id`, `name`, `created_at`, `created_by_user_id`, snapshot payload (JSONB or normalized copy of lesson rows — **design choice documented**)
- [x] `POST /api/v1/timetables/{timetableId}/checkpoints` — body: `{ "name": "..." }`; creates checkpoint of current lesson assignments; 403 if not ADMIN/MODERATOR; 404 wrong tenant
- [x] `GET /api/v1/timetables/{timetableId}/checkpoints` — paginated list of checkpoints (newest first); metadata only or include size — document
- [x] `POST /api/v1/timetables/{timetableId}/checkpoints/{checkpointId}/restore` — transactional restore: replaces current draft lessons from snapshot; idempotent behavior documented; 409 if timetable is **PUBLISHED** (restore only allowed for DRAFT — or product allows with explicit flag — **default: DRAFT only**)
- [x] Retention: enforce **max N checkpoints per timetable** (config property, default e.g. 10) — deleting oldest or rejecting with 400 — match PRD “last 10 checkpoints” guidance
- [x] All operations audited or logged at service level (optional AOP) — defer to EXPORT/audit epic if table not ready
- [x] Integration tests: create lessons → checkpoint → mutate → restore → assert equality with checkpoint state

## Dev Agent Record

### Implementation Plan
- **Snapshot format — normalised copy, not JSONB.** The AC asked for this choice to be documented, and the reasoning is in the V030 header: H2 (tests) and PostgreSQL (production) disagree on JSON handling and this would be the only opaque column in an otherwise relational schema; restore becomes an ordinary delete-and-reinsert rather than parse-then-map; and foreign keys keep a checkpoint from outliving the subjects or rooms it names. The cost is one row per lesson per checkpoint, bounded by retention.
- `POST` / `GET` `/api/v1/timetables/{id}/checkpoints` and `POST .../{checkpointId}/restore`, all ADMIN/MOD.
- **Restore is DRAFT-only** (409 otherwise) — the AC's stated default. Rewriting a published schedule people are already working to should not be one call.
- **Retention drops rather than rejects.** The AC allowed either; deleting the oldest keeps checkpointing frictionless, which matters for a feature meant to be used freely before risky edits. Limit is `app.timetables.max-checkpoints`, default 10, matching the PRD's "last 10 checkpoints".
- Create, restore and retention-drop are each logged at INFO with ids and counts, satisfying the audit AC without a dedicated audit table.

### Completion Notes
- Restore is idempotent: it replaces the lesson set wholesale, so repeating it converges. Verified over three consecutive restores.
- `is_pinned` is captured and restored, so rolling back does not silently unpin work.
- The integration test walks the AC's exact path — create lessons → checkpoint → mutate (move + add) → restore → assert the original state returns.
- `./mvnw -o test -Dtest='TimetableCheckpointEndpointTest'` → 12 passed.
