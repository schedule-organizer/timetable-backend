## Dev Agent Record

### Implementation Plan
- Overrides live in `temporary_schedule_lessons`, never in `lessons`, so the base timetable is untouched and COVER-06 can restore it by deleting rows rather than by reversing edits.
- Date validation is two-stage: `startDate < endDate` (also a DB CHECK), then containment inside the term reached via `base_timetable_id → timetables.term_id → terms`. A range that escapes the term is a 400; a missing timetable is a 404.
- "Only one active per timetable" is enforced in the service (409). A partial unique index on `(base_timetable_id) WHERE status = 'ACTIVE'` would be the DB-level equivalent but is not portable to the H2 setup the tests run on.
- `DELETE` is a hard delete of the overlay plus its overrides — the point of removing an overlay is that the base schedule applies again, so there is nothing worth keeping.
- `UNIQUE (temporary_schedule_id, class_id, schedule_period_id, scheduled_date)` keeps one class from having two overrides in the same slot.

### Completion Notes
- **No write API for overrides.** The AC only requires that overrides are *stored separately*, which the schema and the response's `overrideCount` satisfy. Nothing in Epic 7 specifies how an override is authored, and doing so would mean inventing an endpoint contract; the endpoint test seeds one with SQL, the same approach used for `teacher_preferences` in RES-10. A follow-up story should define override authoring, most naturally alongside SCHED-02's lesson grid.
- `status` is introduced here (ACTIVE/EXPIRED) rather than in COVER-06, since the "only one active" rule needs it and an expired overlay must stop blocking new ones.
- `./mvnw -o test -Dtest='TemporaryScheduleEndpointTest'` → 17 passed.
