## Dev Agent Record

### Implementation Plan
- The `timetables` table already existed from V011 (HOL-05 scaffolding), so this story constrains it rather than creating it: a CHECK pinning status to the three legal states, plus an index for the per-term status lookups the lifecycle rules need.
- Transition rules live in `TimetableStatus.canTransitionTo` so they are stated once and testable in isolation. `DRAFT → PUBLISHED → ARCHIVED`, plus `DRAFT → ARCHIVED` for abandoning a draft outright. Nothing moves backwards, and re-asserting the current status is a 400 rather than a silent no-op.
- "Only one PUBLISHED per term" is maintained on transition: publishing archives whichever timetable was previously published for that term. That is the behaviour SCHED-07 also specifies, so implementing it here keeps the two consistent.
- Status changes go through `PATCH /{id}/status` rather than `PUT`, so a plain edit can never move the lifecycle by accident.
- `bellScheduleId` is optional on the request — the ACs list only name/termId/status — and defaults to the tenant's default bell schedule, 400 if there is none.

### Completion Notes
- Deleting a DRAFT timetable also deletes its lessons. The AC only says hard delete is DRAFT-only, but `lessons.timetable_id` is `ON DELETE CASCADE` in V015, so rows would vanish regardless; doing it explicitly in the service makes the intent visible and keeps the JPA persistence context consistent.
- `update` rejects edits to an ARCHIVED timetable (409). Not in the ACs, but archived is a terminal historical state and silently mutating it would undermine the lifecycle the story defines.
- `findPublishedForTerm` is exposed for SCHED-07 to reuse when it adds the validated publish endpoint.
