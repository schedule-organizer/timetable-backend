# Story RES-08 — Option Blocks CRUD
**Epic:** Epic 5 — Resource Management | **Points:** 4 SP | **Status:** done

## Description
CRUD `/api/v1/option-blocks` — option block containers that enforce simultaneous scheduling of member groups; Flyway migration

## Acceptance Criteria
- [x] CRUD for option blocks (name, description, memberGroupIds[])
- [x] All member teaching groups scheduled at the same period (enforced by solver)

## Dev Agent Record

### Implementation Plan
- Read policy: GET any authenticated user; POST/PUT/DELETE `ADMIN`/`MOD`, matching the rest of Epic 5.
- Minimum-2 members enforced by `@Size(min = 2)` on the request record so it returns a 400 validation envelope.
- Member type check and tenant lookup are one batched `findByIdInAndTenantIdAndActive` call; a missing id is a 404, a wrong type is a 400.
- `UNIQUE (teaching_group_id)` on the junction keeps a group in at most one block; the service pre-checks it to return a 409 with a useful message rather than a constraint-violation 500.
- Solver constraint pairs lessons via `forEachUniquePair`, joins both sides to their `OptionBlockMembership` facts, and hard-penalizes when the two memberships share an option block but the lessons hold different period slots.

### Completion Notes
- `DELETE` deactivates the block **and** clears its `option_block_groups` rows, unlike RES-07's soft delete which keeps membership. Membership only expresses "these groups are co-scheduled"; once the block is gone that is no longer true, and holding the rows would keep the groups locked out of any future block via the unique constraint.
- `Lesson.teachingGroupId` is a new solver-side field. Nothing populates it yet — SCHED-02/03 builds `TimetableSolution` from persisted rows and will set it alongside `teacherUserId` / `subjectId`. Until then the constraint is inert on real data and is covered by the solver test.
- `./mvnw -o test -Dtest='OptionBlockServiceTest,OptionBlockEndpointTest,OptionBlockConstraintSolverTest,TeacherQualificationConstraintSolverTest'` → 27 passed.
