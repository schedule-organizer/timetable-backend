# Story NOTIF-02 — Timetable Published Notification
**Epic:** Epic 8 — Notifications | **Points:** 4 SP | **Status:** done

## Description
`TIMETABLE_PUBLISHED` WebSocket event to `/topic/tenant/{tenantId}/notifications` on publish; personal queue for targeted user notifications

## Acceptance Criteria
- [x] `TIMETABLE_PUBLISHED` event published when timetable status changes to PUBLISHED (SCHED-07)
- [x] Event payload: `{ timetableId, timetableName, termName, publishedAt }`
- [x] Broadcast to `/topic/tenant/{tenantId}/notifications`
- [x] Personal notifications also routed to `/queue/user/{userId}/notifications` for targeted alerts
- [x] Event scoped to tenant (no cross-tenant broadcast)

## Technical Notes
Depends on NOTIF-01. Called from `TimetableService.publish()`.

## Dev Agent Record

### Implementation Plan
- SCHED-07 already emitted `TIMETABLE_PUBLISHED` on the tenant topic. This story completes it: the payload now carries `timetableName` and `termName` as the AC specifies (it previously had only ids), and publication additionally fans out to each active user's personal queue.
- Both the immediate and the future-dated publish paths go through `applyPublication`, so a scheduled publish announces itself identically.
- Recipients are the tenant's ACTIVE users, so deactivated accounts are not notified.

### Completion Notes
- The AC's phrase "personal notifications also routed to `/queue/user/{userId}/notifications` for targeted alerts" is implemented as a fan-out to every active user rather than a filtered subset — nothing in Epic 8 defines who a "targeted" recipient would be. If that should be narrowed (say, only teachers with lessons in the timetable), it needs a product decision.
- Per-user email goes out on the same path, which is where NOTIF-03's timetable-published message is wired.
- Tests: `TimetablePublishedNotificationTest` (3), plus `TimetablePublishEndpointTest` (11) still green.
