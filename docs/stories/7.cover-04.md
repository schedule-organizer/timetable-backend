## Dev Agent Record

### Implementation Plan
- Planning is a pure function separated from persistence, so the conflict check runs against the **complete post-change picture** before any row is written — this is what "validates no conflicts introduced by approval before committing" requires. A clash raises `ConflictException` (409) and the transaction rolls back untouched.
- The conflict rule is that no teacher may end up with two lessons in one (date, period). Slots freed by the same plan are correctly released first, so a straight swap does not report a false clash against itself.
- **SWAP semantics** (undefined in the story): for each requested lesson, the target's lesson *in the same slot* moves back to the requester. Where the target has nothing in that slot, the lesson simply moves across — a swap against an empty slot. A single counterpart is never planned twice.
- Rejection requires a reason; a blank string counts as missing. The V024 CHECK enforces the same invariant at the database level.

### Completion Notes
- `decidedBy` / `decidedAt` are stamped on both outcomes, giving an audit trail the ACs do not ask for but which the schema already supported.
- `DELEGATION_UPDATE` goes to the requester's and the target's personal queues. Publishing is best-effort by design (COVER-07): a broker outage will not roll back a completed reassignment.
- Approval re-checks that the target teacher is still active and that every lesson still exists, since a request can sit PENDING for arbitrarily long before someone decides it.
- `patch_approvalThatWouldDoubleBook_returns409AndChangesNothing` asserts both lessons and the request status are unchanged after the rejection, proving the rollback.
