# Story TMPL-03 — Apply Template to Institution
**Epic:** Epic 10 — Setup Templates (Post-MVP) | **Points:** 4 SP | **Status:** done

## Description
`POST /api/v1/institutions/apply-template` — apply template settings and bell schedule to tenant; idempotent

## Acceptance Criteria
- [x] Accepts: templateId
- [x] Applies template's bell schedule (creates `BellSchedule` + periods for tenant)
- [x] Applies template's settings (locale, timezone, terminology) to tenant settings
- [x] Applies template's constraint defaults
- [x] Idempotent: re-applying same template is safe (upserts, no duplicates)
- [x] Returns preview of changes before applying (with `dryRun=true` query param)
- [x] Admin only

## Technical Notes
Wraps CONFIG-03 and CONFIG-04 logic. Template application does not overwrite manually customised settings if `preserveExisting=true`.

## Dev Agent Record

### Implementation Plan
- Reuses `BellScheduleService.create` (CONFIG-03) and `TenantSettingsService.updateSettings` (CONFIG-04) rather than writing rows directly, so template application obeys the same validation as manual configuration.
- **Idempotence by replacement**: a same-named bell schedule is deleted and recreated instead of a second being added, so re-applying converges rather than accumulating. Verified over three consecutive applications.
- `dryRun=true` builds the identical change list and returns before any write, so the preview cannot drift from what applying would actually do — the two share one code path.
- `preserveExisting=true` filters the update down to keys the institution has not already set, so a customisation is never silently overwritten.

### Completion Notes
- ADMIN only, not ADMIN/MOD: applying a template reshapes the whole institution's configuration.
- Tests: covered by `TemplateEndpointTest`, including that a customised timezone survives an apply with `preserveExisting`.
