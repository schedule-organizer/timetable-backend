# Story COVER-03 — Submit Delegation Request
**Epic:** Epic 7 — Cover, Delegation & Temporary Schedules | **Points:** 3 SP | **Status:** done

## Description
`POST /api/v1/delegation` — teacher submits SWAP or HANDOVER request for one or more lessons; Flyway migration

## Acceptance Criteria
- [x] Accepts: type (SWAP/HANDOVER), lessonIds[], targetTeacherId (for SWAP), reason
- [x] Creates delegation request with status PENDING
- [x] SWAP: proposes exchange of lessons between two teachers
- [x] HANDOVER: permanently transfers lesson responsibility
- [x] Teacher can only delegate their own lessons
- [x] `V024__create_delegation_requests.sql` Flyway migration included
- [x] Returns 404 if any lessonId or targetTeacherId not found in tenant

## Dev Agent Record

### Implementation Plan
- Any authenticated user may submit, but only for lessons whose `teacher_user_id` is their own — the AC is unconditional, so this applies to ADMIN and MOD too. A foreign lesson raises `AccessDeniedException` → 403.
- Ownership is checked across the whole batch before anything is written, so a mixed request never half-persists (covered by `post_mixOfOwnAndOthersLessons_returns403`).
- A lesson already named in a PENDING request cannot be claimed by a second one (409), otherwise two approvals could reassign the same lesson twice.
- A DB CHECK keeps `rejection_reason` consistent with `status`: present iff REJECTED. COVER-04 relies on this.

### Debug Log
- `post_asAnotherTeacher_cannotDelegateRequestersLessons` first failed 400 instead of 403: the second teacher was also the *target*, so the self-delegation guard fired before the ownership check. Retargeted the request at a third party so it reaches the check under test.

### Completion Notes
- **`targetTeacherId` is required for HANDOVER as well as SWAP**, deviating from the AC's "(for SWAP)" parenthetical. COVER-04's AC says an approval "reassigns all lesson records to target teacher" for both types, and its PATCH body carries only a decision and a rejection reason — so if HANDOVER had no target, an approved handover would have nobody to transfer to. Requiring it for both is the only reading under which the two stories are jointly implementable. `NOT NULL` in the schema.
- SWAP vs HANDOVER only differ at *decision* time; submission records the intent identically. The exchange semantics are defined and implemented in COVER-04.
- No WebSocket event on submission: COVER-07 and COVER-04 specify `DELEGATION_UPDATE` on a decision, and no AC asks for one here. Notifying the target that a request awaits them would be a reasonable follow-up.
- `./mvnw -o test -Dtest='DelegationRequestEndpointTest'` → 14 passed.
