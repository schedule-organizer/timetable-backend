# Story SCHED-08 — Move Lesson (Drag & Drop)
**Epic:** Epic 6 — Timetable & Scheduling Engine | **Points:** 3 SP | **Status:** done

## Description
`PATCH /api/v1/lessons/{id}` — move lesson to new period/room via drag-and-drop; run conflict detection; broadcast WebSocket event

## Acceptance Criteria
- [x] Accepts: new periodId, new roomId (both optional, at least one required)
- [x] Runs `ConflictDetectionService` on proposed move before committing
- [x] Conflict detection covers: teacher double-booking, room double-booking, class double-booking, room capacity, forbidden slots
- [x] Commits move and returns updated lesson with `hasConflict` flag
- [x] Broadcasts `LESSON_UPDATED` WebSocket event (SCHED-12)
- [x] Returns 404 if lesson or timetable not found in tenant

## Technical Notes
Optimistic locking on lesson record to prevent concurrent edits. Admin/Mod/Teacher (own lessons) can move.

## Dev Agent Record

### Implementation Plan
- **Conflicts are reported, not blocking.** The AC says to run detection before committing and return the lesson with a `hasConflict` flag — which only makes sense if the move lands. A moderator dragging a card may knowingly create a temporary clash while rearranging. What *is* rejected is an invalid request: no fields supplied, or an unknown period or room.
- Optimistic locking via the `@Version` column added in V027 (SCHED-11's migration), so two concurrent drags cannot silently overwrite each other.
- Access mirrors the rest of the codebase: ADMIN/MOD may move any lesson, other roles only lessons they teach.

### Completion Notes
- The response carries the full `ConflictViolation` list, not just a boolean, so the UI can explain what it collided with.
- Tests: `LessonMutationEndpointTest` (20, covering SCHED-08/09/10 together).
