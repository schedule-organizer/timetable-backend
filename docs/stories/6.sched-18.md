# Story SCHED-18 — Planning Model and Core Clash Constraints
**Epic:** Epic 6 — Timetable & Scheduling Engine | **Points:** 8 SP | **Status:** ready-for-dev

## Description
Extend the Timefold planning model so the solver can express — and therefore avoid — the clashes that
`ConflictDetectionService` already catches on manual edits.

`SchediFlowConstraintProvider` currently defines three constraints: holiday slot, teacher
qualification, option-block co-scheduling. The planning `Lesson` (`solver/model/Lesson.java`) carries
`teacherUserId`, `subjectId`, `teachingGroupId`, `pinned` and `periodSlot` — **no `classId`, no
`roomId`**. Teacher, class and room double-booking are therefore not merely unpenalised, they are
inexpressible. A solve can place every lesson in the same slot and score zero hard violations.

The asymmetry is the real defect: `ConflictDetectionService` rejects a *manual* move that the
*solver* is free to make. FR19 ("engine satisfies hard and soft constraints") is not met until this
lands, and FR36 ("engine treats preferences as soft, forbidden as hard") is not met at all.

**Traceability:** FR19, FR36; deferred-work.md "Solver fidelity" section (carried from Epic 5 and not
closed by Epic 6).

## Dependencies
- **SCHED-17** (lesson generation) is a strict prerequisite — there is nothing to constrain until a
  timetable has a realistic lesson set. Use its demo fixture as the test bed.

## Acceptance Criteria
- [ ] Planning `Lesson` gains `classId` and `roomId`; `SolverProblemBuilder` populates both
- [ ] Hard constraint: **teacher double-booking** — no two lessons sharing `teacherUserId` in one `PeriodSlot`
- [ ] Hard constraint: **class double-booking** — no two lessons sharing `classId` in one `PeriodSlot`
- [ ] Hard constraint: **room double-booking** — no two lessons sharing a non-null `roomId` in one `PeriodSlot`
- [ ] Hard constraint: **forbidden slots** — `UnavailablePeriodPenalty` is re-keyed to carry an entity (teacher/class/room) instead of a bare slot, so `ForbiddenSlotService.findAllForSolver` finally feeds the solver (closes the Epic 5 carry-over)
- [ ] Soft constraint: teacher `workload_cap` and `max_periods_per_day` overrun
- [ ] Soft constraint: subject `spread_pattern` (SPREAD / CLUSTER) and `max_per_day`
- [ ] Every new constraint has a `ConstraintVerifier` unit test proving it penalises and that a clean case scores zero
- [ ] Integration test: a full solve over the SCHED-17 demo fixture (756 lessons) ends with **zero hard violations**, verified by re-running `ConflictDetectionService` over the persisted result — solver and API must agree
- [ ] Constraint names are stable strings; `scoreBreakdown` (SCHED-04) reports them per constraint

## Technical Notes
- Renaming "Holiday slot must be free" was already flagged in deferred-work once
  `UnavailablePeriodPenalty` covers non-holiday unavailability — do it here.
- The solver/API agreement test is the important one. It is the only assertion that catches the two
  code paths drifting apart again.
- Room placement as a *planning variable* (rather than a pre-assigned fact) is explicitly **out of
  scope** — this story only stops the solver double-booking rooms that generation already assigned.
  A room-assignment story comes after.
