# Story RES-10 — Teacher Availability View
**Epic:** Epic 5 — Resource Management | **Points:** 2 SP | **Status:** done

## Description
`GET /api/v1/teachers/{id}/availability` — returns forbidden slots + soft preferences for a teacher

## Acceptance Criteria
- [x] Returns combined view: forbidden slots (hard unavailability) + soft preferences
- [x] Soft preferences: PREFERRED_FREE, PREFERRED_TEACHING (advisory only for solver)
- [x] Returns 404 if teacher not found in tenant
- [x] Response structured as weekly grid (dayOfWeek × periodId → availability status)
- [x] All authenticated roles can read own availability; Admin/Mod can read any teacher's

## Technical Notes
Joins `forbidden_slots` and `teacher_preferences` (if implemented). Teachers can only read their own via role check.

## Dev Agent Record

### Implementation Plan
- Grid rows are weekdays `1..daysInCycle` read from tenant settings `schedulingCycle.daysInCycle` (default 5, clamped to 1–7) via `TenantSettingsService.getSettings`, rather than re-parsing the raw settings blob.
- Grid columns are every period of the default bell schedule in ordinal order — break and lunch periods included, so a forbidden slot on one is never silently dropped. No default bell schedule → 400, matching `ClassSubjectHourService`.
- Cell status precedence: a recurring forbidden slot (`UNAVAILABLE`) always overrides a preference; otherwise the preference value; otherwise `AVAILABLE`.
- Access mirrors RES-09: ADMIN/MOD read any teacher, everyone else only the teacher profile mapped to their own user id.
- An unparseable `preference_type` row is logged at WARN and ignored rather than failing the request (same defensive pattern as `ClassSubjectHourService.toResponse`).

### Completion Notes
- Date-specific (one-off) forbidden slots cannot be expressed in a repeating weekly grid, so they are returned in a separate `dateSpecificUnavailability` list. Without this the view would silently omit hard unavailability, which the "combined view" AC rules out.
- **Known gap, unchanged by this story:** `teacher_preferences` has no write endpoint. The implementation-readiness report already flags FR34 ("TEACHER declares soft availability preferences") as having no story — RES-10 is read-only by specification. Preferences are therefore only settable by direct SQL today, which is how the endpoint test seeds them. A follow-up story is needed to close FR34.
- `./mvnw -o test -Dtest='TeacherAvailabilityServiceTest'` → 13 passed; `-Dtest='TeacherAvailabilityEndpointTest'` → 11 passed.
