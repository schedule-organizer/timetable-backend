## Dev Agent Record

### Implementation Plan
- Two queries for the whole grid, neither scaling with lesson count: one joined projection for the rows, one batched conflict pass. The three filters are applied inside the same query with `:param is null or ...` guards, so every filter combination is still one query.
- `Room` is an outer join because a lesson may be unroomed; `roomName` comes back null rather than dropping the row.
- `hasConflict` reuses SCHED-11's rules through a new batched entry point rather than a second implementation. `checkConflicts` and `hasConflictByLessonId` share the same private comparison helpers, so the grid flag and what a move would report can never disagree.
- `dayOfWeek` is derived in Java from `scheduledDate` rather than in JPQL, avoiding a database-specific date function.

### Debug Log
- Two tests failed with the teacher's email instead of their name. The query took `users.display_name`, but an invited user has none — the scheduling display name lives on the **teacher profile** (RES-04). Added a left join to `Teacher` and made the name `coalesce(teacher.displayName, user.displayName, user.email)`, which is the more correct source anyway.

### Completion Notes
- `teacherId` filters by `teachers.id` for consistency with the rest of the API, resolved internally to the `teacher_user_id` lessons actually carry. A `teacherId` matching nobody returns an empty grid rather than silently ignoring the filter and returning everything — covered by `get_unknownTeacherFilter_returnsEmptyRatherThanEverything`.
- The response includes `scheduledDate` alongside `dayOfWeek`. The AC lists only `dayOfWeek`, but lessons are stored against real dates, and a weekday alone cannot identify which week a card belongs to.
- `./mvnw -o test -Dtest='TimetableGridEndpointTest'` → 14 passed.
