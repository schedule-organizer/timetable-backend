# Story SCHED-17 — Lesson Generation from Curriculum Allocations
**Epic:** Epic 6 — Timetable & Scheduling Engine | **Points:** 8 SP | **Status:** ready-for-dev

## Description
Materialise the lesson set for an empty timetable from the curriculum already captured in `class_subject_hours` (RES-06) and the staffing already captured in `teaching_groups` (RES-07).

Every Epic 6 story to date assumes lessons exist. `SolverProblemBuilder.build` reads
`lessonRepository.findByTenantIdAndTimetableId…` and derives its placeable date range from the dates
those rows already occupy (`SolverProblemBuilder.java:87-90`); an empty timetable therefore solves
instantly with nothing to place. Cover, delegation and temporary-schedule overlays all operate on
lesson rows that, today, only tests insert. This story closes the gap between "the solver rearranges
a timetable" and "the product produces one".

**Traceability:** FR18 (MODERATOR initiates generation), FR19 (hard/soft satisfaction), RES-06
(`class_subject_hours`), RES-07 (`teaching_groups`). Recorded as a scope gap in
`_bmad-output/implementation-artifacts/deferred-work.md` under the Epic 6 section.

## Scope boundary — read before implementing
Generation alone does **not** produce a usable timetable, and this story must not claim it does.

`SchediFlowConstraintProvider` defines exactly three constraints — holiday slot, teacher
qualification, option-block co-scheduling. There is **no teacher, class or room double-booking
constraint**, and the planning `Lesson` (`solver/model/Lesson.java`) carries no `classId` and no
`roomId`, so those clashes cannot be expressed at all. Double-booking is caught only by
`ConflictDetectionService`, on manual moves, after the fact.

Consequence: hand 756 freshly generated lessons to `POST /api/v1/engine/run` today and Timefold may
legally stack every one of them into Monday period 1 and report a **perfect score with zero hard
violations**. That is a truthful reading of the current constraint set, not a solver bug.

This story therefore delivers *correct input*. Making the solver produce a *correct arrangement* is
**SCHED-18 — Planning model and core clash constraints**, which must land before generation is
demonstrated end to end. SCHED-17 is a strict prerequisite of SCHED-18 (there is nothing to constrain
until lessons exist), and SCHED-18 is a strict prerequisite of calling FR19 satisfied.

## Design decisions
Settled before implementation; recorded here so the ACs are not re-litigated in review.

**Horizon — one cycle week.** Generation materialises the 6 dates of the term's first full teaching
week, not every teaching date in the term. 21 classes × 36 periods = 756 rows, which is what
`SolverProblemBuilder` already treats as the placeable range. Generating the whole term would be
~12,000 planning entities per timetable and a different performance problem. Repetition across the
term is a publication/export concern.

**Staffing — `teaching_groups` are required.** A `teaching_group` already means *this teacher teaches
this subject to these classes*. Generation reads `class_subject_hours` for **what** and
`teaching_groups` for **who**. A `(class, subject)` allocation with no active group is a **422**
listing every gap, not a silent auto-assignment: choosing who teaches what is a head-of-department
decision, and inventing it at generation time would compete with the solver's own load balancing.

**Room — homeroom or nothing.** The solver has no room planning variable, so generation does not
pretend to place rooms. A lesson whose subject has no `required_room_type` gets the class's
`homeroom_id`; one that needs a `LAB`/`GYM`/`OTHER` gets `room_id = NULL` for a later story to place.
Homeroom assignment cannot double-book, because a homeroom belongs to exactly one class.

**Date/period assignment — deterministic, arbitrary, unsolved.** Generated lessons must occupy a slot
because `scheduled_date` and `schedule_period_id` are `NOT NULL`. Generation lays them out in a
stable round-robin over (date × teaching period) per class, which guarantees no *class* self-clash
but says nothing about teacher or room clashes. This is a starting position for the solver, and the
response must describe it as such.

## Acceptance Criteria
- [ ] `POST /api/v1/timetables/{id}/generate-lessons` — ADMIN/MODERATOR only; **403** for TEACHER; tenant isolation via `TenantContext` as everywhere else
- [ ] Reads `class_subject_hours` for every active class in the tenant and emits `periods_per_cycle` lesson rows per `(class, subject)` allocation
- [ ] Teacher is resolved from the active `teaching_group` for that `(class, subject)`; `lessons.teaching_group_id` is populated (requires the new column — see T1)
- [ ] A `(class, subject)` allocation with no active teaching group → **422** naming every unstaffed pair; **no rows are written** (whole call is one transaction)
- [ ] Cycle dates are the 6 teaching dates of the term's first full week, skipping any date in the tenant's holiday calendar; if fewer than 6 teaching dates remain in the term → **422**
- [ ] Lessons are laid out round-robin over (date × non-break, non-lunch period) per class, so no class is double-booked in its own generated set
- [ ] `room_id` = class `homeroom_id` when the subject has no `required_room_type`, otherwise `NULL`
- [ ] Refuses to run on a non-`DRAFT` timetable → **409**; refuses when the timetable already has lessons → **409** with a pointer to the regenerate flag
- [ ] `?replace=true` clears the existing generated lesson set first, in the same transaction; pinned lessons (SCHED-09) are **preserved** and their slots excluded from the round-robin
- [ ] Response reports `lessonsCreated`, `classesCovered`, `periodsPerClass`, `unstaffedPairs: []`, and an explicit `placement: "UNSOLVED"` marker so no caller mistakes the output for a solved timetable
- [ ] Demand/supply summary is returned or logged: total periods demanded vs. teaching slots available per class, so an over-subscribed curriculum (e.g. 40 periods into 36 slots) fails loudly with **422** rather than silently dropping lessons
- [ ] `@Audited` on the generation method — it is a bulk write a moderator must be able to account for
- [ ] `LESSON_UPDATED` broadcast to `/topic/timetable/{id}` once after generation, so an open grid reflects the new set (SCHED-12)
- [ ] Integration test on the demo fixture (see T6) asserts exactly 756 rows, 21 classes × 36 periods, every lesson carrying a teacher and a teaching group, and no class double-booked

## Technical Notes
- **Schema:** `lessons` has no `teaching_group_id` column. Adding one closes a defect carried since
  RES-08 — `Lesson.teachingGroupId` exists on the planning entity and drives
  `optionBlockGroupsMustShareAPeriod`, but nothing has ever populated it, so that constraint has been
  inert on real data since it was written. Nullable column + FK, additive per NFR14.
- **Volume:** 756 rows in one transaction. Use `saveAll` in batches; do not flush per row.
- `SolverProblemBuilder` needs no change — it already reads whatever lessons exist. That is the point
  of generating into the same table rather than inventing a parallel "unplaced lesson" concept.
- Reuse `HolidayService` for the holiday-date exclusion rather than re-querying `holiday_dates`.
- The 422-on-unstaffed-pairs response is the main UX surface of this story: it is how a timetabler
  discovers their staffing is incomplete. Make the message enumerate pairs, not just count them.

## Demo fixture (T6) — built, and configurable
The dataset the ACs are asserted against, already in the tree:

- `src/main/resources/application-demo.yml` — the school shape, and the only place it is defined
- `com.schediflow.config.DemoDataProperties` — binds `app.demo`
- `com.schediflow.service.DemoDataSeeder` — builds it; `seed(slug)` for tests, `seed()` for startup
- `DemoDataSeederTest` / `DemoDataSeederConfigTest` — 14 tests pinning the arithmetic

Run it: `SPRING_PROFILES_ACTIVE=demo ./mvnw spring-boot:run`, then sign in as
`admin@demo-school.demo` / `DemoPassw0rd!`. Tests set `app.demo.auto-seed=false` and seed per test
under a unique slug.

The seeder refuses to build a school that cannot work, and says which key to change:

| Bad edit | Result |
|---|---|
| Curriculum no longer fills the cycle | `demands 36 periods per class but the cycle offers 30 …` |
| Teacher pool under the workload cap | `… over the workload cap of 34. Raise subjects[MATH].teachers to 5` |
| Subject missing a field | `app.demo.subjects[0] is missing 'code' …` |

That last one matters more than it looks: overriding a single field of a YAML list element replaces
the whole list rather than merging into it, so a half-specified subject is an easy accident.

The shipped configuration — an Armenian/European secondary school, grades 6–12:

| Dimension | Value |
|---|---|
| Classes | 21 — grades 6–12 × sections A, B, C |
| Cycle | 6 days (Mon–Sat) × 6 teaching periods + 1 lunch = 36 teaching slots/class |
| Curriculum | 11 subjects summing to exactly 36 periods/class/week |
| Lessons/cycle | 21 × 36 = **756** |
| Teachers | 30 |
| Mean teacher load | 756 / 30 = **25.2 periods/week** (~70% of the 36-slot maximum) |
| Peak teacher load | 33 periods — `workload_cap` seeded at 34 |
| Teaching groups | 21 classes × 11 subjects = **231** |
| Rooms | 33 — 21 homerooms, 8 labs, 2 gyms, 2 art rooms |

Curriculum, per class, per 6-day cycle:

| Subject | Periods | Required room |
|---|---|---|
| Mathematics | 6 | — (homeroom) |
| Language & Literature | 5 | — |
| English | 4 | — |
| Physics | 3 | LAB |
| Chemistry | 3 | LAB |
| Biology | 3 | LAB |
| History | 3 | — |
| Geography | 2 | — |
| Computer Science | 2 | LAB |
| Physical Education | 3 | GYM |
| Art & Music | 2 | OTHER |
| **Total** | **36** | |

Teacher pools sized so no teacher exceeds `workload_cap`: MATH 5, LANG 4, ENG 3, PHYS 2, CHEM 3,
BIO 2, HIST 3, GEO 2, CS 2, PE 2, ART 2 = **30**.

Because the shape is configuration, a different school is a YAML edit — `DemoDataSeederConfigTest`
covers a 12-class primary on a 5-day, 5-period week (300 lessons) to prove it. Note that the ACs
above quote the *shipped* numbers; retuning the fixture means retuning them too, which is what
`shippedConfigurationDescribesTheSchoolTheStoryClaims` exists to catch.

Two properties make this fixture worth its weight:
- **It is feasible but tight.** 70% teacher utilisation is above the 50–65% a real school runs, so a
  solver that ignores teacher clashes will look fine and a correct one will have to work.
- **Lab demand is over-supplied on purpose.** PHYS+CHEM+BIO+CS = 231 lab lessons over 36 slots = 6.4
  concurrent; 8 labs leaves headroom, so room placement (a later story) starts from a solvable
  position rather than an impossible one.
