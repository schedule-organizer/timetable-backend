# Story SCHED-04 — Solver Job Status Polling
**Epic:** Epic 6 — Timetable & Scheduling Engine | **Points:** 2 SP | **Status:** done

## Description
`GET /api/v1/engine/jobs/{id}` and `GET /api/v1/engine/jobs` — poll job status, quality score, score breakdown, error message; job history per timetable

## Acceptance Criteria
- [x] `GET /api/v1/engine/jobs/{id}` returns: jobId, timetableId, status, qualityScore, scoreBreakdown, startedAt, completedAt, errorMessage
- [x] Job statuses: QUEUED, RUNNING, COMPLETED, FAILED, CANCELLED
- [x] `GET /api/v1/engine/jobs?timetableId=...` returns paginated job history
- [x] Returns 404 if job not found in tenant
- [x] Quality score formatted as: hard violations count + soft score
- [x] Score breakdown lists top constraint violations

## Technical Notes
`solver_jobs` table. Solver listener updates status on each best-solution event.

## Dev Agent Record

### Implementation Plan
- `GET /api/v1/engine/jobs/{id}` and a paginated `GET /api/v1/engine/jobs?timetableId=`, newest first, reusing the project's `PagedResponse`.
- `qualityScore` is rendered as `"N hard / M soft"`; `scoreBreakdown` states feasibility in words. Timefold reports violations as a negative hard score, so the count is surfaced as a positive number.
- Status is written by the solver callbacks, so polling reflects live progress without the API touching the solver.

### Completion Notes
- `scoreBreakdown` summarises rather than enumerating per-constraint counts. Timefold can produce per-constraint detail through score analysis, which costs an extra scoring pass; deferred until there is a UI that needs it.
- Tests: covered by `EngineEndpointTest`.
